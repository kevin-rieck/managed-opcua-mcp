# OPC UA SDK evidence for native-write migration, slice B

This records SDK research from slice B and the isolated protocol evidence subsequently added in slice E. A/B/C/D are present in the current unstaged checkout. This is not evidence that the separate inspection specification or the entire release/cutover gate has passed; final independent review and release acceptance remain pending.

## Versions and trust

The installed lockfile resolves `node-opcua`, `node-opcua-client`, `node-opcua-secure-channel`, and `node-opcua-certificate-manager` to **2.174.0**. The direct `node-opcua` dependency is pinned to 2.174.0 because the native single-dispatch path below depends on a private SDK method. Review the actual installed dependency graph and rerun the bridge tests before any upgrade.

`node_modules/node-opcua-client/dist/private/client_base_impl.js`, constructor and `connect`/`fetchServerCertificate`, uses `getDefaultCertificateManager("PKI")` when none is supplied and, for secure mode, checks the discovered server certificate using that manager before opening the secure channel. `node_modules/node-opcua-certificate-manager/dist/certificate_manager.js` shows that the SDK default manager enables `automaticallyAcceptUnknownCertificate: true`; its explicit manager defaults differently, but this adapter now supplies an `OPCUACertificateManager` with `automaticallyAcceptUnknownCertificate: false`. Its `checkCertificate` rejects unknown/untrusted certificates and does not accept unknown revocation when that flag is false. The adapter does not downgrade security mode or policy; invalid/contradictory pairs fail client construction.

The explicit manager uses the SDK manager's default root (`env-paths("node-opcua-default").config`, not the former default manager's `PKI` subdirectory). Operators must provision the trusted server or issuer and applicable revocation material in that manager's trusted PKI store before secure connection. Existing trust under the old location is not silently copied. `securityMode: None` remains intentionally insecure and is not protected by server-certificate authentication. The existing unit tests cover configuration and manager branches with stubbed verification. The slice E test below additionally exercises a genuine self-signed secure endpoint and its certificate with temporary stores. It does not test CA chains, CRLs, expiry, or site deployment trust material.

The installed SDK client increments its manager's `referenceCounter` on construction. Its disconnect calls manager `dispose()` without awaiting it; at a counter of one this only decrements the counter, and an already-disconnected failed client can skip that call altogether. The adapter's idempotent disconnect releases its internally created manager after SDK disconnect, including when disconnect throws, first releasing any remaining SDK references, including the temporary secure-endpoint discovery client. A synchronous client-construction failure also schedules cleanup of the internally created, uninitialized manager. Injected managers remain caller-owned; the adapter does not add a dispose call for them. On the tested refused-connect path the installed SDK can leave an injected manager's reference counter incremented, so its owner must account for that SDK behavior when disposing it.

`tests/opcua/pki-cleanup.test.ts` runs a child with temporary environment-path roots and the installed manager and PKI registry. It observes at least three initialized owned managers from automatic failed secure reconnect attempts, including a manager with at least two SDK references from endpoint discovery, verifies each reaches the SDK disposed state, and checks `CertificateManager.checkAllDisposed()`. It separately verifies an initialized injected manager remains active after failure and gateway close, and that the caller can dispose it, including any SDK-retained reference. Unit coverage exercises disconnect and client-construction exceptions. This is a refused-loopback and exception test, not proof for every shutdown race or SDK version. After this fix the focused cleanup/trust/protocol/stdio run passed 5 files / 10 tests; `npm run check` passed 22 files / 139 tests with 3 external tests skipped.

## Write request and reconnect

`node_modules/node-opcua-client/dist/private/client_session_impl.js`, `write` and `performMessageTransaction`/`#reprocessRequest`, wraps a WriteRequest in a transaction queue and retries `BadSessionIdInvalid`, potentially after `session_restored` or session recreation. Therefore public `session.write` is unsuitable for the native-write no-replay contract. The native bridge constructs an SDK `WriteRequest` containing a NodeId constructed directly from validated components, and calls the installed session's private `_performMessageTransaction` once. An absent seam fails closed; there is no public-write fallback. The legacy catalog write path was removed in C/D.

The same SDK private method first checks channel validity, attaches the session token and calls `ClientBaseImpl.performMessageTransaction` once. `node_modules/node-opcua-client/dist/private/client_base_impl.js` forwards once to the secure channel. `node_modules/node-opcua-secure-channel/dist/source/client/client_secure_channel_layer.js` creates one request record and sends it; timeout/response handling completes or drops that transaction rather than reissuing it. This source inspection and a focused test using the installed `ClientSessionImpl` on `BadSessionIdInvalid` support the bridge design. Slice E additionally exercises a real lost response and invalid session over loopback, as described below; neither proves all disconnect/timing paths.

The SDK secure-channel `process_request_callback` puts a `ServiceFault` in `error.response`; other failed service responses may be passed as the callback response. The bridge preserves either exact numeric service StatusCode when present, without treating it as a per-node rejection; missing or malformed operation statuses remain unconfirmed. Exceptions without a service StatusCode remain ambiguous after invocation. For ordinary failed `ReadResponse`/`BrowseResponse`, `_performMessageTransaction` passes the response separately, and the public wrappers or promise discard it. The session adapter retains that response on the error at the public transaction callback before those wrappers discard it, without parsing SDK error text; the real client fails closed if that transaction seam is absent. Installed-session regression tests cover both response types through the gateway and MCP. Numeric severity, not a name, governs status decisions.

## Slice E isolated protocol acceptance

`tests/integration/isolated-opcua-protocol.test.ts` runs by default: an in-process `node-opcua` 2.174.0 Server binds `127.0.0.1` on port 0, uses a test-owned temporary server PKI, and creates independent, sequential MCP instances for the `reader` and `writer` username/password principals. Credentials are fixture-only. No site config, external endpoint, site audit file, or user/default trust store is used. The audit sink records in memory. Each client has its own temporary PKI; sessions, clients, managers, server, environment overrides, and directories are cleaned up. The fixture drains retained SDK references before disposing its own client managers, including the secure manager reused after an untrusted connection, and checks the installed PKI active-instance registry after server shutdown. The protocol and owned-cleanup tests passed together twice after this fixture correction (2 files / 5 tests each); a fresh full check passed 22 files / 139 tests with 3 external tests skipped, and the build passed.

## Stdio transport diagnostic regression

Before the correction, `tests/integration/stdio-diagnostics.test.ts` ran the real CLI `serve` path in a child with an installed SDK logger fixture: injected secret-bearing SDK diagnostic lines appeared on stdout, and parsing every stdout line as JSON failed. The post-fix test uses test-owned config, audit and environment-path/PKI roots and a refused loopback endpoint (`127.0.0.1:1`). It performs real stdio initialization, tool listing and status reads, waits for the structured disconnected connection error, parses all stdout lines as JSON-RPC, and checks that fixture values, NodeId and password appear in neither stream. No external endpoint or user/default trust store is used.

The fixture invokes the installed SDK's debug, warning, error and trace logger functions with sensitive arguments. It also forces an exception in the installed `node-opcua-pki` certificate verification method, exercising its direct `console.log` warning path while asserting its unchanged `BadCertificateInvalid` result. Direct console log/warn/error/info/debug/trace calls are tested as well. All observed stderr lines must be fixed diagnostic categories; arguments are not serialized. The separate real loopback protocol test continues to exercise actual trust rejection, secure connection and exact numeric read/write outcomes.

SDK hooks are installed before the gateway loads `node-opcua`, including the trace hook exported by the installed `node-opcua-debug` package. The stdio bootstrap additionally owns the process console, since SDK PKI and secure-channel paths call it directly. Inspection of installed `node-opcua-*` JavaScript found PKI `process.stdout.write` paths gated by `VERBOSE` and/or `NODEOPCUAPKIDEBUG`; the dedicated stdio bootstrap clears both before SDK loading. This disables those SDK PKI debug modes for the process. It does not control arbitrary direct stream writes, prior SDK initialization by an embedding host, uncaught runtime errors, or future dependency changes. `createMcpServer` does not take console ownership; embedding `startMcpServer` does. Gateway logger hooks are process-wide. The normal CLI `doctor` against the same kind of isolated refused endpoint produced valid JSON, exit 4 and fixed SDK stderr with debug modes disabled; this is one path, not a general safety claim for all doctor diagnostics.

Focused transport/protocol/trust/contract validation passed **5 files / 11 tests**. `npm run check` passed **21 files / 137 tests**, with 3 external tests skipped, and `npm run build` passed. The final manager/reviewer gate remains open.

## Remaining risks and cutover work

- The real loopback tests cover one server implementation, selected failures, self-signed trust, and a bounded reconnect window; they do not establish behavior for every server, CA/revocation setup, process crash, network timing, or physical action.
- The single-dispatch bridge uses the SDK's private `_performMessageTransaction` and depends on the pinned SDK. Inspect and retest the installed bridge on upgrades.
- The full release/cutover gate remains open pending independent review and final checks; see the [migration acceptance record](opcua-native-migration-acceptance.md). This is not a claim of complete inspection-spec conformance.
- External endpoint tests remain explicitly opt-in and were not run. No production endpoint was contacted.
